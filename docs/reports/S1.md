# S1 속도 정비 — 보고서

## 쉬운 말 다섯 줄
1. **같은 게임이 훨씬 빨라졌습니다.** 새 기능은 없습니다. "50년 뒤 마을"에서 50년 넘기기가 **164초 → 93초(CPU 1개) → 59초(CPU 4개)**, 사람 300명 · 100년이 **543초 → 264초 → 154초**입니다(같은 클라우드 컴퓨터).
2. 느렸던 까닭을 먼저 쟀습니다. 가장 무거웠던 것은 **물 · 먹을 것 · 재료를 둘레에서 찾을 때 매번 넓은 땅을 다 훑던 것**과 **지방 지도를 잊었다가 다시 만들던 것**이었습니다 → 찾는 길을 줄이고 지도를 더 많이 기억하게 했습니다(결과는 똑같이).
3. 이제 **지방마다 다른 CPU 가 계산**합니다. 지방끼리는 6분(게임 시간)마다 한 번만 주고받아서, **CPU 를 1개 쓰든 4개 쓰든 똑같은 세계**가 됩니다(테스트로 확인). 게임 위 막대 오른쪽 **[CPU 3/4]** 단추로 바꿀 수 있고, 기본은 "코어 수 − 1"입니다.
4. 세계의 흐름은 전과 거의 같습니다 — 시드 20개 × 200년에서 토기 · 지식 끊김과 되찾음 · 인구 · 죽음 원인 · 팝업 수가 ±10% 안입니다. **모닥불이 3년 빨라졌고(19.5 → 16.5년) 정신 붕괴가 조금 늘었는데(+15%)**, 같은 새 코드로 다른 시드 20개를 돌려 보면 이 정도는 시드 묶음마다 흔들리는 양이었습니다(아래 표). 다만 모닥불은 두 번 다 더 일찍 나와서, 정말 빨라진 것인지 다음 측정 때 한 번 더 봐야 합니다.
5. 한 단계 측정에 걸리는 시간이 **약 5시간 → 72분**이 되었습니다(목표 1시간에는 조금 못 미침). 저장 파일 형식이 9번으로 바뀌었고 옛 파일(장면 포함)도 읽습니다.

## 해 볼 것
1. zip 을 풀고 **`WTW.exe`** 를 실행합니다(윈도우가 "PC 보호" 경고를 띄우면 **"추가 정보 → 실행"**). **[불러오기] → "50년 뒤 마을" → [넘기기] → 50년.** 전에는 이 컴퓨터 계산으로 약 2분 40초 걸리던 것이 1분 안쪽이면 성공입니다(화면 그리기가 더해져 실제로는 조금 더 걸릴 수 있습니다). 끝난 뒤 걸린 시간을 알려 주세요.
2. **5배속**으로 두고 사람이 많을 때(위 "50년 뒤 마을"을 넘긴 뒤) 화면이 끊기지 않는지, 윈도우 **작업 관리자**에서 CPU 가 여러 개 쓰이는지 봐 주세요. 위 막대 오른쪽 **[CPU n/m]** 를 누르면 CPU 수가 바뀝니다(1이면 예전처럼 하나만).
3. 같은 장면에서 전처럼 발견 · 알림이 나오는지 — "그동안 일어난 일" 창에 세계에서 처음 발견 · 무리에서 끊김 · 새 땅으로가 전과 비슷하게 뜨는지 봐 주세요.

## 2. 한 CPU 에서 빠르게

### (가) 결과가 똑같은 정비 — 고정 지문(`SpeedTests.PinnedFamilies` · `PinnedVillage`, 그리고 300명 3년 지문)이 바뀌지 않음을 하나씩 확인
| 무엇 | 어떻게 |
|---|---|
| 지방 지도를 잊었다가 다시 만듦 | 기억해 두는 지도 64장 → **512장**(지도는 언제나 같게 다시 만들어지므로 결과는 같다. 메모리 +약 100MB — 아래) |
| 경계 너머 보이는 물 찾기(판단마다) | 이웃 지방의 물가 수천 개를 다 훑던 것 → 16타일 묶음 **색인**(같은 거리면 앞 변 · 작은 번호 — 훑을 때와 같은 답) |
| 둘러보기의 물가(SightTiles 14) | 지도로만 정해지므로 **타일마다 한 번만** 찾고 기억(바위를 캐 이어진 땅이 바뀌면 지움) |
| 가까운 먹을 것 · 그늘 · 돌 · 재료 · 주울 것 | 15타일 묶음 가운데 **네모 안 가장 가까운 점도 더 먼 묶음은 건너뜀** |
| 재료 · 주울 것 찾기 | 오브젝트 **종류별 색인** — 맞는 종류의 타일만 본다 |
| 땅에 놓인 물건 찾기 | 놓인 자리가 많으면 둘레 20타일 네모만 번호 순으로(처음 맞는 것이 같다) |
| 아이템 이름 → 번호 | 목록을 문자열로 훑던 것 → **표**(오브젝트가 주는 것도 한 번만 계산) |
| 불의 따뜻함(사람마다 시간마다) | 정렬 사전을 훑던 것 → 바뀔 때만 다시 만드는 **배열** |

| 아이 밴 사람 세기 | 맞추는 시각마다 모든 사람을 훑던 것 → 셈을 따로 둠 |
| 난수 스트림 찾기 | 문자열 열쇠 사전 → 지방에 기억 |

### (나) 결과가 조금 바뀌는 정비
"덜 자주 하기"(무리 셈 · 가르치기 판단 간격 · 불 돌보기 몰아서)는 **하지 않았습니다** — 재 보니 셋 다 몫이 1~3%라 줄여도 얻는 것이 없었고, 결과만 바뀝니다. 결과가 바뀐 것은 지방마다 CPU 구조 때문뿐입니다(3절):
1. **같은 시각의 일 순서**: 예전에는 세계 전체가 한 줄로 (시각, 예약 순번) 순이었고, 이제는 지방마다 따로 같은 순서다. 하루 경계의 하루 일은 그 시각의 예약 · 넘겨주기 뒤로(전에는 앞).
2. **세계의 일은 맞추는 시각에**: 알림 · 세계에서 처음 발견 · 말의 새 낱말 · 별명 · 그림 번호 · 지식의 역사 · "거의 될 뻔" 목록이 최대 6분(게임 시간) 늦게 세계에 남는다. 같은 6분 안에 두 지방이 같은 것을 처음 알아내면 (시각, 칸 번호) 순으로 먼저인 쪽이 "세계에서 처음"이다. 세계에서 처음 알아낸 사람의 "남겨 두고 싶음"도 이때 생긴다.
3. **사람 상한 셈**: 지방 계산 중에는 다른 지방을 볼 수 없으므로 "지난 맞추는 시각의 산 사람 + 아이 밴 사람"에 "그 뒤 이 지방에서 생긴 아이"만 더한다(여러 지방이 같은 6분에 아이를 가지면 상한을 한두 명 넘을 수 있다 — 300명 100년 측정에서 가장 많을 때 301명).
4. **다른 지방 사람을 보던 곳을 막음**(버그 고침): 이야기 · 수업 상대 · 안은 사람 · 먹으려던 시체 · 젖먹이 아이가 그 사이 다른 지방으로 갔는데도 그 사람의 위치(다른 지방 좌표)를 보던 곳 → 같은 지방일 때만.

고정 지문은 이 구조 변화 때 한 번 새 값으로 바꿨습니다(`sim.tests/SpeedTests.cs` 에 고친 기록).

## 3. 지방마다 CPU (E8 에서 앞당김)

- **맞추는 시각** = 넘겨주기 시각(게임 6분, 하루 240번) — **간격은 그대로** 두었습니다. 지방 계산은 맞추는 시각까지 지방마다 따로(지방마다 **예약표**를 따로 둠), 맞추는 시각에 한 줄기로: 미뤄 둔 세계의 일 적용 → 넘겨주기 → (하루 경계면) 하루 일.
- **E3b 가 남긴 "지방끼리 주고받는 것" 정리**

| 것 | 어디로 |
|---|---|
| 가족(짝 · 부모 · 아이 따라가기) | 하루 경계(한 줄기)에서만 다른 지방을 본다. 지방 계산 중 가족을 볼 때는 같은 지방일 때만(2절 4번) |
| 짝 찾아보기 · 짝이 됨 | 같은 지방 안(원래 그랬음) |
| 말 표(낱말 · 빌려 온 낱말 · 별명) | 맞추는 시각에(미룬 일). 지방 계산 중에는 읽기만 |
| 땅 이름 표 · 말의 갈라짐 | 하루 경계(원래 그랬음) |
| 말 쓰는 사람 수 세기 | 그 지방 사람만 |
| E4 발견 목록 · 거의 될 뻔 · 무리마다 처음 | 맞추는 시각에 |
| E5 지식의 역사 · 그림 | 맞추는 시각에(그림을 그리는 손은 그 자리에서, 그림 번호와 목록은 맞추는 시각에) |
| 무리 셈 · 세계에서 사라짐 | 하루 경계(원래 그랬음) |
| 알림 | 맞추는 시각에 (시각, 칸, 차례) 순으로 번호를 붙인다 |
| 측정 셈 · 죽은 사람 수 · 처리한 예약 수 | CPU 마다 모았다가 더한다 |
| 경계 · 지방 지도 · 난수 스트림 | 처음 만들 때만 잠그고(누가 만들어도 같은 것) 함께 읽는다 |

- **검사**: 지방 계산 중에 다른 지방을 만지면 그 자리에서 멈춘다(실수를 바로 찾게). 빠른 테스트 · 수천 년치 측정 동안 한 번도 걸리지 않았다.
- **같은 결과**: `SpeedTests.FourThreadsSameAsOne`(지방 6곳 · 45일 — 경계 수십 번, CPU 1 = 4), `VillageThreadsSame`(큰 마을 1 = 3), `SaveMidSyncThenContinueWithThreads`(맞추는 시각 사이 — 미룬 일이 있을 때 — 저장 → 불러오기(CPU 2) → 계속 = 끊김 없이), 느린 테스트 `SpeedSlowTests`(300명 · 지방 20곳 · 6년, 경계 288번 · 지방 깨어남 29번, CPU 1 = 4, 3년째 저장 → CPU 2 로 계속). 측정 도구에서도 300명 100년 · 넘기기 50년의 지문이 CPU 1 = 4.
- **CPU 나누기**: 일꾼 스레드를 세워 두는 묶음(`ProvincePool`). 부를 때마다 Parallel.ForEach 를 쓰는 것보다 빠름(300명 8년: 28.7초 → 24.7초).
- **게임**: CPU 수 = 코어 수 − 1(화면 몫), 위 막대 오른쪽 **[CPU n/m]** 로 바꾸고 기억(`user://settings.cfg`). 측정 도구는 `--threads N`, `--threads auto`(4절).
- **저장 버전 9**: 지방마다 예약표 · 다음 예약 번호(잠든 지방도 — 잠들었다 깨어나도 번호가 이어지게) · 미뤄 둔 세계의 일 · 상한 셈 기준 · **깨어 있던 지방**. 마지막 것은 이번에 찾은 옛 버그다: 사람이 다 죽고 아직 잠들지 않은 지방이 불러오면 잠든 지방이 되어 불 · 들불이 멈췄다(저장 → 불러오기 → 계속이 어긋남). 버전 8 이하 파일(시험용 장면 포함)도 읽는다.

## 4. 측정 자체를 빠르게
- `--parallel N`(시드를 CPU 에 나눔)과 `--threads N`(한 세계를 CPU 여러 개로)을 함께 쓸 수 있다. **`--threads auto`** 는 돌고 있는 세계 수로 코어를 나눠 세계마다 CPU 수를 날마다 다시 정한다(끝 무렵 시드 몇 개만 남으면 남은 세계가 코어를 더 쓴다). CPU 수는 결과와 상관없다.
- 새 측정 모드 `people skip --scene … --years N`(장면을 불러와 넘기기처럼), `discover --save`, `cap --save`, 정신 붕괴 셈, 메모리 정리(GC) 셈.

## 기획과 다르게 한 것 / 이유
- **기획서 5-5 "지방끼리는 하루 경계에서만 주고받는다"** → 이미 E3b 부터 넘겨주기는 6분마다였고, 이번에 세계 전체의 일도 그 6분 시각에 맞췄다(하루 경계만으로는 경계를 넘는 사람이 너무 오래 서 있게 된다 — E3b 의 결정을 따름). 간격은 바꾸지 않았다.
- **(나) "덜 자주 하기"는 하지 않음** — 재 보니 해당 일의 몫이 작아(1~3%) 결과만 바뀌고 빨라지지 않는다.
- **지도 기억 64 → 512장**: 메모리를 약 100MB 더 쓰는 대신 지도를 다시 만들지 않는다(게임 화면도 같은 기억을 쓴다).
- **기획서 4절 "시뮬은 별도 스레드"** → 시뮬 스레드 하나 + 지방 계산 일꾼(코어 수 − 2개). 화면 몫으로 하나를 남긴다.

## 알려진 문제 · 다음 단계에 넘길 것
- **CPU 4개에서 1.6~1.7배** — 하루 일 · 넘겨주기 · 지방 깨우기가 한 줄기, 지방 크기가 고르지 않음, 맞추는 시각이 하루 240번. 더 빠르게 하려면 하루 일을 지방마다 나누기 · 지방 지도 만들기를 미리(빈 CPU 로) · 맞추는 간격 늘리기(기획 결정).
- **불러온 직후 느림**: 지방 지도는 저장하지 않으므로 불러오면 깨어 있는 지방과 그 이웃의 지도를 다시 만든다(넘기기 첫 몇 년에 지도 만들기가 40%까지). 지도 만들기 자체를 빠르게(잡음 계산) 하면 좋다 — 결과가 소수점까지 같아야 해서 이번에는 손대지 않음.
- 쌀쌀한 땅을 여럿 함께 돌릴 때 565µs(목표 500) — 남은 것은 재료 구하기 · 주변 찾기.
- 한 단계 측정 72분(목표 60분) — 따뜻한 땅 200년이 48분. 다음에 `--threads auto` 와 함께 CPU 4 효율이 오르면 맞출 수 있다.
- 구간별 시간 재기는 측정용 사본에만(`tools/profile/instrument.py`) — 다음 단계도 같은 표로 비교할 수 있다.
- **모닥불이 더 일찍 나오는지**(위 표) — 고치기 전 코드로 다른 시드 묶음을 재 보면 가릴 수 있다.
- 숫자 튜닝 때: 무리에서 한 사람만 아는 법 10.5%(목표 ~17%) · 되찾기까지 2.2년(3년) · 구리 0/20 — 이번 단계 이전부터.
